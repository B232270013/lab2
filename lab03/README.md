# Лаборатори №3: Чанарын сценарио → SLO → k6 threshold

|---|---|
| Тойм | Хэрэглэгч барааг сагсандаа нэмэхэд систем хурдан хариулна. |
| Системийн төлөв | API ажиллаж байгаа, POST /cart/add хүсэлт хүлээн авахад бэлэн. |
| Орчны төлөв | Локал WSL2; 20 VU, 1 минут. VU бүр /cart/add, /report, /pay руу дараалан хүсэлт илгээж, давталтын дараа 1 секунд хүлээнэ. Хүсэлт/с тогтмол биш. |

## 2. Reliability — Төлбөрийн найдвартай байдал

| Хэсэг | Тодорхойлолт |
|---|---|
| Тойм | Төлбөрийн хүсэлтийн алдааны давтамж зөвшөөрсөн босгоос бага байна. |
| Системийн төлөв | API ажиллаж байгаа; /pay нь хүсэлт бүрд ойролцоогоор 5% магадлалаар HTTP 500 буцаана. |
| Орчны төлөв | Локал WSL2; 20 VU, 1 минут. VU бүр гурван endpoint руу дараалан хүсэлт илгээж, давталтын дараа 1 секунд хүлээнэ. Хүсэлт/с тогтмол биш; серверийг зориуд зогсоохгүй. |
| Гадаад өдөөлт | Хэрэглэгч хэвийн төлбөрийн үйлдлээр POST /pay хүсэлт илгээнэ. |
| Шаардлагатай хариу | HTTP 200 болон {"paid":true} буцаана. |
| Хэмжүүр | http_req_failed{name:pay} хэмжүүрийн error rate < 8%. Энэ API-ийн туршилтад HTTP 500 болон холболтын алдаа бүтэлгүй хүсэлтэд тооцогдоно. |

## 3. Availability — Сервер эвдрэлийн дараа сэргэх

| Хэсэг | Тодорхойлолт |
|---|---|
| Тойм | Серверийн тасалдал нийт хүсэлтийн амжилтад хэрхэн нөлөөлөхийг шалгана. |
| Системийн төлөв | API эхэндээ ажиллаж байгаа; тусдаа терминалаас зогсоож дахин асаана. |
| Орчны төлөв | Локал WSL2; 20 VU, 2 минут. VU бүр гурван endpoint руу дараалан хүсэлт илгээнэ; хүсэлт бүрийн timeout 2 секунд, давталтын дараах хүлээлт 1 секунд. |
| Гадаад өдөөлт | Тест ажиллаж байх үед серверийг Ctrl+C-ээр зогсоож, sleep 10 командаар хүлээсний дараа node server.js ажиллуулна. |
| Шаардлагатай хариу | Дахин ассан сервер хүсэлтүүдэд HTTP 200 буцааж, үйлчилгээ сэргэнэ. |
| Хэмжүүр | Гурван endpoint-ийн нийт HTTP 200 хариуны хувь ≥ 95%. Сэргэх хугацааны зорилт ≤ 10 секунд бөгөөд зогсоосон мөчөөс анхны HTTP 200 хүртэл хэмжинэ. |

Сэргэх хугацааны зорилт нь одоогийн k6 кодод автомат threshold
болоогүй, хэмжилт нь дутуу байна. sleep 10 нь зөвхөн хүлээлтийн
хугацаа бөгөөд нийт тасалдал, бодит сэргэх хугацаатай тэнцүү биш.

|---|---|
| Итгэмжтэй | Сагсанд нэмэх, төлбөр хийх, сервер зогсох нь бодит хэрэглээнд тохиолддог. |
| Үнэ цэнэтэй | Хүлээлт, төлбөрийн алдаа, үйлчилгээний тасалдлыг хэмжинэ. |
| Тодорхой | Endpoint, HTTP арга, өдөөлт, хүлээгдэх хариуг заасан. |
| Нарийн | Ачаалал, тестийн хугацаа, алдааны хувь, percentile болон сэргэх хугацааны хязгаарыг тоогоор заасан. |
| Ойлгомжтой | Сценарио бүрийг ижил 6 хэсэгтэй хүснэгтээр бичсэн. |

## Сценарионоос гаргасан SLO

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency | p95 < 20 мс | 20 VU, 1 минут; серверийг зогсоохгүй |
| Reliability | /pay error rate | < 8% | 20 VU, 1 минут; серверийг зогсоохгүй |
| Availability — үндсэн | Гурван endpoint-ийн нийт HTTP 200 хариуны хувь | ≥ 95% | 20 VU, 1 минут; серверийг зогсоохгүй |
| Availability — chaos | Гурван endpoint-ийн нийт HTTP 200 хариуны хувь | ≥ 95% | 20 VU, 2 минут; серверийг зогсоож, 10 секунд хүлээгээд дахин асаана |
| Report performance | /report latency | p95 < 450 мс | 20 VU, 1 минут; серверийг зогсоохгүй |

Chaos тестэд үндсэн дөрвөн threshold хэвээр үйлчилнэ.
Зориудын FAIL хувилбарт зөвхөн /report-ын босгыг p95 < 100 мс
болгож, 20 VU, 2 минутын турш серверийг зогсоохгүй ажиллуулна.


### Босго сонгосон үндэслэл

- Cart: Эхний хэмжилтийн p95 2.07 мс байсан тул орчны хэлбэлзэлд зай үлдээж, удаашралыг илрүүлэх 20 мс босго сонгосон.
- Reliability: Серверт ойролцоогоор 5% алдаа зориуд суулгасан тул санамсаргүй хэлбэлзлийг тооцож 8% босго сонгосон.
- Availability: Үндсэн туршилтад нийт хүсэлтийн хамгийн багадаа 95% нь HTTP 200 хариу авах шаардлага тавьсан.
- Report: Зориудын 200–400 мс саатал дээр нэмэлт боловсруулалтын хугацааг тооцож 450 мс босго сонгосон.

### Availability-ийн хугацаагаар тооцсон error budget

Томьёо:

Error budget = Ажиглалтын хугацаа × (1 − Availability зорилт)

Тооцоо:

120 секунд × (1 − 0.95) = 6 секунд

Иймээс 2 минутын цонхонд хугацаанд суурилсан 95%-ийн
availability зорилтын зөвшөөрөх нийт тасалдал 6 секунд байна.

## Алхам 4 — PASS туршилтын үр дүн

20 VU, 1 минутын тохиргоотой туршилтаар нийт 2778 хүсэлт
илгээснээс 2729 нь HTTP 200, 49 нь алдаатай хариу авсан.

/cart/add-ийн p95 = 2 мс, /report-ийн p95 = 393.05 мс.
/pay-ийн 926 хүсэлтээс 49 нь алдаатай буюу error rate = 5.29%.
Нийт хүсэлтийн амжилтын хувь = 98.23%.

Дөрвөн threshold бүгд PASS, k6 exit code = 0.
Үр дүнгийн файл: results/pass.txt.

Энэ туршилтад серверийг зориуд зогсоогоогүй тул crash-ийн дараах
сэргэх хугацаа болон тасалдалтай үеийн availability-г хараахан шалгаагүй.

## Алхам 5 — Мини chaos — availability сценариогоо бодитоор турших

Терминалдаа хугацааг өөрчилсөн <br>
sed -i "s/duration: '1m'/duration: '2m'/" slo-test.js


20 VU, 2 минутын тохиргоотой тестийн явцад серверийг
зогсоож дахин асаасан.

### Availability ба error budget

- Нийт хүсэлт: 5832
- Амжилттай хүсэлт: 4532
- Бүтэлгүй хүсэлт: 1300
- Availability = 4532 / 5832 × 100 = 77.71%
- k6-ийн дэлгэцэд 77.70% гэж харагдсан.
- Зорилт: ≥ 95% → FAIL

Хүсэлтээр тооцсон error budget:
5832 × 0.05 = 291.6 буюу хамгийн ихдээ 291 бүтэлгүй хүсэлт.

Бодит 1300 алдаа нь зөвшөөрөх бүхэл тоон хязгаарыг
1009 хүсэлтээр хэтрүүлсэн.

Хугацаагаар тооцсон budget:
120 × 0.05 = 6 секунд.

Төлөвлөсөн 10 секундийн зогсолт нь өөрөө 6 секундийн
budget-ээс их тул 95%-ийн хугацаанд суурилсан зорилттой нийцэхгүй.
Зорилтыг хадгалахын тулд тасалдлыг богиносгох шаардлагатай.

### Хугацааны ба хүсэлтийн budget яагаад ялгаатай вэ?

Сервер ажиллах үед /report 200–400 мс хүлээлгэдэг.
Сервер унтарсан үед холболтын алдаа хурдан буцаж,
энэ хүлээлт алга болдог тул VU бүр илүү хурдан давталт хийнэ. Иймээс тасалдлын үед нэг секундэд илгээх хүсэлтийн тоо өсөж, хүсэлтээр хэмжсэн алдааны хувь хугацааны тасалдлын хувиас ялгаатай гардаг. Мөн /pay-ийн зориудын 500 алдаанууд нийт хүсэлтийн budget-ийг давхар зарцуулдаг.

### Reliability яагаад мөн FAIL болсон бэ?

/pay-ийн 1944 хүсэлтээс 476 нь бүтэлгүй буюу 24.48% болсон.
Энэ хэмжүүрт зориудын 500 алдаа болон серверийн тасалдлын
үеийн холболтын алдаа хамт орсон тул 8%-ийн босгыг давсан.

SLI-үүдийг тусгаарлахын тулд availability-г тусгай health
шалгалтаар, төлбөрийн reliability-г HTTP хариу авсан
төлбөрийн хүсэлтүүдийн бизнес амжилтын хувиар хэмжиж болно.

Серверийг Ctrl+C-ээр зогсоож, дараа нь `date -Is`,
`sleep 10`, `node server.js` командуудыг дараалан ажиллуулсан.
10 секундийн хүлээлт оруулсан боловч команд оруулах болон
сервер асах хугацаа нэмэгдэх тул нийт тасалдал яг 10 секунд
байсан гэж үзээгүй. Сэргэх бодит хугацааг энэ удаа нарийн
хэмжээгүй.

Хүсэлтээр хэмжсэн availability 77.71% болж 95%-ийн зорилтыг,
төлбөрийн error rate 24.48% болж 8%-ийн босгыг тус тус зөрчсөн.

## Алхам 6 — Зориудын FAIL туршилт

Скрипт: slo-test-fail.js
Нөхцөл: 20 VU, 2 минут; серверийг зогсоохгүй.

| Threshold | Босго |
|---|---|
| http_req_duration{name:cart} | p(95)<20 |
| http_req_failed{name:pay} | rate<0.08 |
| checks | rate>=0.95 |
| http_req_duration{name:report} | p(95)<100 |

/report нь 200–400 мс зориудын сааталтай тул 100 мс-ийн
босгыг зөрчихөөр тохируулсан. Бусад босгыг хэвээр үлдээсэн.
Гаралтыг results/fail.txt файлд хадгалсан.

### Бодит үр дүн

/report-ын p95 = 390.11 мс байсан нь зориуд тавьсан
p95 < 100 мс босгыг зөрчсөн. Бусад гурван threshold PASS болсон.

k6 нь threshold зөрчигдсөнийг error мөрөөр мэдээлж,
exit code 99 буцаасан. CI pipeline энэ тэгээс ялгаатай
exit code-ийг алдаа гэж боловсруулан тухайн алхмыг унагаана
(алдааг үл тоохоор тусгайлан тохируулаагүй үед).

/cart/add-ын p95 = 1.78 мс тул p95 < 50 мс гэсэн босго
тавьсан ч PASS хэвээр байх байсан.

## Дүгнэлт

Энэ лабораториор чанарын сценариог хэмжигдэхүйц SLO болгон тодорхойлж, k6 threshold-оор автоматаар шалгасан.
Хамгийн хэцүү нь сценарионы ачаалал, хэмжүүр, босгыг кодын тохиргоотой зөрүүлэхгүй байлгах байсан.
Эхний хэмжилтэд тулгуурлан сагсанд нэмэх үйлдлийн босгыг чангаруулж, хэвийн ачаалалд дахин шалгасан.
Үндсэн туршилтын дөрвөн threshold бүгд PASS болсон.
Chaos туршилтаар нийт хүсэлтийн амжилтын хувь 95%-ийн зорилтыг хангаагүй тул тасалдалтай нөхцөлд тавьсан availability шаардлага биелээгүй.
Энэ нь хэмжүүрийг үгүйсгэсэн бус, тухайн нөхцөлд систем зорилтоо хангахгүй байгааг харуулсан.
Хугацаанд суурилсан error budget болон хүсэлтэд суурилсан budget нь тасалдлын үед хүсэлтийн хурд өөрчлөгддөг учраас шууд тэнцдэггүй.
Серверийн тасалдал төлбөрийн хүсэлтүүдийг мөн унагасан тул availability ба reliability хоёр SLO зэрэг зөрчигдсөн.
Тайлангийн босгыг зориуд бууруулахад k6 exit code 99 буцаасан нь CI-д шаардлага зөрчсөн тестийг автоматаар илрүүлэх боломжийг харуулсан.
